BSM / private publishing system

Operator's
field guide.

How an article travels from the /admin dashboard to a per-revision GitHub pull request, through owner review and a merge to main, and finally onto a fully static Cloudflare site.

A practical manual · settled operating model (ADRs 0008–0013) · read before configuring production

Read this first

Migration status

This guide documents the operating model in effect. The D1/Keystatic-era machinery (Keystatic routes and config, the postinstall patch, the D1 CMS_DB binding, migrations, the drafts save/list API, and the manual deploy dispatch) has been removed; the CMS is GitHub-native per ADRs 0009–0013. publish.ts was absorbed into draft-publish.ts — provenance now lives in the PR metadata fingerprint created at PR time.

The central distinction

“Publishing” in this CMS means merging a reviewed pull request to main. There is no separate deploy button: every merge auto-deploys. GitHub is the durable source of truth for content, revisions, and PR metadata; the small Worker runtime exists only for admin authentication, GitHub mutations, and deployment confirmation. The public site is fully static.

The system is therefore a deliberately reviewed chain:

01 · AUTHOREdit in the /admin dashboard. The browser holds a local draft, not a GitHub token.
02 · REVISION“Save revision & open PR” commits to cms/<slug>/r<N> and opens a pull request.
03 · REVIEWThe PR diff is the review surface. A new revision supersedes the older PR.
04 · MERGEThe owner merges to main. Merged PRs are immutable.
05 · DEPLOYGitHub Actions builds and deploys the static site automatically.
06 · LIVEThe signed callback records the deployed SHA; the CMS marks the revision Published.

1. The architecture in one page

There are four actors. Keeping their responsibilities separate is what prevents an editor click from becoming an unreviewed production change.

Actor What it owns What it must never receive
Editor browser Dashboard authoring, local autosave, media upload, PR lifecycle status. GitHub PATs, Cloudflare API tokens, callback secrets, or the owner secret.
Astro / Cloudflare Worker Sessions, GitHub branch/commit/PR mutations, PR metadata, provenance verification, deployment-confirmation callback. Nothing is sent back to the browser except opaque session state and API results.
GitHub Repository history, blog files and media, branches, pull requests, Actions, and repository secrets. The owner’s CMS session or arbitrary callback destinations.
Cloudflare Workers + Assets runtime, session KV + deployed-SHA KV, and the public site. The editor’s raw GitHub token.

The repository’s server build is a split Astro output: static files are written to dist/client/; the Cloudflare Worker is written to dist/server/. The generated dist/server/wrangler.json is the deployment config used by the workflow.

Why not Pages?
The adapter output is Worker + Assets. Classic flat-output Pages deployment expects a different shape and is not the target for this setup.

The relevant implementation seams are:

  • src/pages/admin/login.astro — owner sign-in; the dashboard lives at /admin.
  • src/utils/draft-publish.ts — per-revision branch + PR creation and the PR metadata block.
  • src/utils/draft-publish.ts — revision branch + PR creation, the PR metadata fingerprint, and the main-source reader for the editor.
  • src/utils/deploy.ts — the deployment-confirmation callback (deployed SHA).
  • .github/workflows/deploy.yml — auto-deploy on push to main, then signs a callback.
  • wrangler.toml — Worker name, compatibility, and the SESSION KV binding.

2. Roles and approval boundaries

The dashboard may display editor/owner distinctions, but the role switch is only a client-side demonstration until server-enforced roles are implemented (the GitHub App hardening step). Today all CMS API guards check for a valid admin session, and the owner-secret session is the only production credential. Treat the owner access key accordingly.

Editor

An editor writes content in the dashboard and creates revision pull requests. That is the extent of an editor’s reach: nothing an editor does changes main or the live site. “Ready” is a content state, not a server-enforced permission boundary.

Owner

The owner supplies the access key at /admin/login. The server compares it against CMS_OWNER_SECRET, creates a random session ID, and stores the GitHub credential behind that session in the SESSION KV namespace. The browser receives only the HttpOnly bsm-cms-session cookie. The owner reviews PRs on GitHub and merges them — merging is the approval that triggers deployment.

Operational rule

Do not paste a GitHub token into the browser, into a blog field, into a workflow input, or into a checked-in file. If a token has appeared in a browser console, URL, screenshot, or commit, revoke it and issue a replacement.

3. The authoring and publishing flow

  1. Sign in. Visit /admin/login and enter the owner access key. You land on the /admin dashboard.
  2. Write in the dashboard. The editor is a markdown-first WYSIWYG (headings, lists, links, quotes, inline styles). Edit title, kicker, excerpt, body, slug, stable ID, publishedAt, status, aliases, and the featured image. Autosave is browser-local only: nothing reaches GitHub until you explicitly save a revision.
  3. Add media per the contract. The contract (ADR 0011) targets src/images/blog/<slug>/ (featured image cover.<ext>, body images 01-<name>.<ext>…), only JPEG/PNG/WebP, ≤ 5 MB and 8000 px longest edge, CMS-generated names, and required alt text. Uploading from the Media dialog (/api/cms/media) validates magic bytes and dimensions server-side, writes the file to the pending revision branch (cms/<slug>/r<N>), and lists both staged and merged assets. The picker also draws from the existing repo-backed pool.
  4. Save revision & open PR. The CMS validates the post payload, records the referenced media in the PR metadata block, creates branch cms/<slug>/r<N> from main, commits the serialized Markdown, opens a draft pull request, and supersedes older open PRs.
  5. Review on GitHub. The PR diff is the review surface. If a new revision is saved while an older PR is still open, the older PR is closed as superseded with a comment linking the new one. Closed-unmerged PRs are never reopened; merged PRs are immutable.
  6. Owner merges. Merging to main is the approval. GitHub Actions auto-builds and deploys the static site.
  7. Published. The deploy workflow posts a signed callback with the deployed commit SHA; the CMS upgrades every merged revision whose merge commit is deployed to Published.
Provenance, not trust

After a merge, the CMS recomputes the SHA-256 of the merged file and compares it with the fingerprint recorded in the PR metadata block at PR-creation time. Any drift is flagged “changed since review” and is never presented as published.

4. Revisions, branches, and the PR metadata block

Every durable fact about a revision lives in GitHub itself — there is no content database.

  • Branch naming encodes the revision: cms/<slug>/r<N>.
  • Revision discovery lists PRs filtered by the head prefix cms/<slug>/ (robust even after branch deletion), plus branch listing while branches exist. The live revision is the highest N with an open PR; the maximum N overall gives the next revision number.
  • PR metadata block — a versioned HTML comment in the PR body, invisible in the GitHub UI: 
<!-- bsm-cms:revision v1 -->
storageSlug: cara-memilih-pagar-brc
revision: 4
contentFingerprint: sha256:<64-character-hex>
media: [blog/cara-memilih-pagar-brc/cover.jpg]

The block is written at PR creation and parsed for status reconciliation and the post-merge exact-match check. If it is ever absent, the CMS falls back to branch-name parsing.

Lifecycle states

State Meaning What to do
Draft Browser-local only Keep editing; nothing is on GitHub yet.
In review A PR is open for the latest revision Review the PR diff on GitHub; merge when ready.
Merged The revision is in main, queued for deploy Wait for the auto-deploy; verify the site.
Published Deployment confirmed for the merge commit Nothing — the live site serves this revision.
Superseded Closed-unmerged PR replaced by a newer revision Ignore; the newer PR owns the review. Never reopened.

Published is never derived from GitHub alone: it requires the deployed SHA recorded in KV plus an ancestry check against the merge commit (ADR 0010).

5. What GitHub Actions actually does

The workflow is .github/workflows/deploy.yml. It is triggered by every push to main — there are no manual dispatch inputs anymore. The old stage/trigger/dispatch machinery and its CMS_GITHUB_ACTIONS_PAT secret are removed.

  1. Trigger on merge. on: push: branches: [main] fires once per merged PR.
  2. Check out main. The merge commit is the source of truth for the build.
  3. Install and build. bun install --frozen-lockfile, then bun run build. The build creates dist/client/ and dist/server/wrangler.json.
  4. Deploy. bunx wrangler deploy --config dist/server/wrangler.json using the repository’s Cloudflare credentials.
  5. Report the deployed SHA. A final step posts a signed callback with the deployed commit SHA and terminal status, so the CMS can upgrade revisions to Published. 
on:
  push:
    branches: [main]

# The deployment target is the generated adapter config:
bunx wrangler deploy --config dist/server/wrangler.json

6. The signed deploy callback

GitHub Actions calls /api/cms/deploy/callback after the deployment step. The body names the deployed commit and a terminal status: 

{"commitSha":"<40-character-git-sha>","status":"succeeded"}

# or
{"commitSha":"<40-character-git-sha>","status":"failed","error":"GitHub Actions deployment failed."}

The workflow signs the timestamp and raw JSON body with HMAC-SHA256:

message = timestamp + "." + rawJsonBody
signature = "sha256=" + HMAC_SHA256(CMS_DEPLOY_CALLBACK_SECRET, message)

x-bsm-deploy-timestamp: <unix-seconds>
x-bsm-deploy-signature: sha256=<64-character-hex-hmac>

The Worker accepts the callback only when:

  • the timestamp is an integer within five minutes of the current time;
  • the HMAC is valid for the exact raw body;
  • the body contains a well-formed commit SHA and a terminal status.

The accepted callback is written to KV as the last deployed SHA. The CMS then marks Published every merged revision whose merge commit is an ancestor of that SHA. Duplicate terminal callbacks are idempotent.

A healthy end state

A revision PR is merged, the Actions run is green, the callback records the deployed SHA, the dashboard shows Published, and the fully static site serves the merged content.

7. Rollback (revert PRs)

Undoing a published change is a first-class action, not a history rewrite.

  1. The owner triggers a revert PR from the dashboard for a merged revision.
  2. The CMS computes the inverse diff of that revision (Markdown and the media it added) and opens a revert PR against main.
  3. The revert PR flows through the same review → merge → auto-deploy path.

Git history is never rewritten; every production change — forward and backward — is reviewed and auditable. Unreferenced orphan images left by a revert are kept; cleanup is out of scope.

8. One-time production setup

Do the bootstrap in this order. The first deployment may be performed manually with Wrangler if the Worker does not exist yet; subsequent content changes deploy through the PR → merge → Actions path. The repository currently contains a production-looking SESSION namespace ID; do not replace it casually, because changing the namespace invalidates sessions and stored CMS state.

  1. Install the expected toolchain. Use Node >=22.12.0 and Bun (the repository’s configured Bun version). Run bun install.
  2. Confirm the KV namespace. If this is a new environment, run npx wrangler kv namespace create SESSION and put the returned ID in wrangler.toml. For the existing environment, verify the current ID and binding. The binding name must remain SESSION.
  3. Set Worker secrets. Use the commands below. Never commit values to wrangler.toml.
  4. Set repository Actions secrets. These are separate from Worker secrets, although the callback values must match exactly.
  5. Build and make the first deployment. Run bun run build, then bunx wrangler deploy --config dist/server/wrangler.json from a trusted environment. Confirm the Worker URL and the callback route exist.
  6. Log in. Visit /admin/login, enter the owner access key, and confirm the redirect to /admin.
  7. Run a small real smoke test. Make a harmless revision PR, merge it, watch Actions, and confirm the callback upgrades it to Published.

Worker secrets

# From the repository root, authenticated to the target Cloudflare account
wrangler secret put CMS_GITHUB_PAT
wrangler secret put CMS_OWNER_SECRET
wrangler secret put CMS_DEPLOY_CALLBACK_URL
wrangler secret put CMS_DEPLOY_CALLBACK_SECRET

GitHub repository Actions secrets

Secret Value / purpose
CLOUDFLARE_API_TOKEN A narrowly scoped Cloudflare token allowed to deploy the Worker and Assets.
CLOUDFLARE_ACCOUNT_ID The account containing the second-shepherd Worker.
CMS_DEPLOY_CALLBACK_URL Exactly the deployed Worker URL plus /api/cms/deploy/callback.
CMS_DEPLOY_CALLBACK_SECRET Exactly the same random value as the Worker secret.
Removed with the migration

CMS_GITHUB_ACTIONS_PAT and CMS_GITHUB_ACTIONS_DISPATCH_SECRET (manual workflow dispatch) and the D1 CMS_DB binding are gone. KEYSTATIC_GITHUB_PAT is renamed CMS_GITHUB_PAT. The GitHub App installation identity (ADR 0008) will replace the PAT for repository mutations as the next hardening step.

9. Local development and safe testing

Local Astro development does not use the Cloudflare runtime adapter. The application reads development variables from the process environment while using in-memory session/state stores. This is useful for a smoke test, but it is not a production-like persistence test.

Local safety boundary

Use fake credentials and a local mock GitHub API for this test. If CMS_GITHUB_API_URL is omitted in development, the app defaults to the real GitHub API and could create real branches and PRs if real credentials are loaded. 

CMS_OWNER_SECRET='local-owner-secret' \
CMS_GITHUB_PAT='local-github-token' \
CMS_DEPLOY_CALLBACK_URL='https://example.test/api/cms/deploy/callback' \
CMS_DEPLOY_CALLBACK_SECRET='local-callback-secret' \
CMS_GITHUB_API_URL='http://127.0.0.1:4344' \
bun run dev

For an end-to-end local PR test, run a mock GitHub API on the port you configure above. The CMS_GITHUB_API_URL override is development-only; production always calls https://api.github.com.

Before deploying a change, run:

bun install
bun run build
bunx astro check

The project’s build is the authoritative check for the Worker adapter output. If astro check reports existing project diagnostics, separate those from errors introduced by the change.

10. Troubleshooting by symptom

Symptom Likely cause First check
CMS authentication is not configured Worker lacks the owner secret or the GitHub PAT. Check CMS_OWNER_SECRET and CMS_GITHUB_PAT, then redeploy.
CMS session storage is unavailable The SESSION KV binding is missing or has the wrong ID. Compare wrangler.toml with the KV namespace and redeploy.
PR creation returns 422 Branch already exists or content conflicts on the revision branch. Reconcile the PR; the revision branch is meant to be written once. Do not force-update a merged branch.
PR creation is rejected for media The dangling-reference gate found an image reference that does not resolve on the revision branch (or fails the media contract). Upload the referenced image in the Media workspace first, then retry; the gate reports the exact unresolved path.
Dashboard shows “changed since review” The merged file does not match the PR metadata fingerprint. Do not treat it as published; investigate what changed between review and merge.
Merged but not Published The callback was lost or rejected. Inspect the Actions run’s callback step; verify the two callback secrets are byte-for-byte identical.
Callback returns 401 Timestamp too old or HMAC mismatch. Callbacks must be freshly signed; never replay an old callback verbatim.
Every route returns 500 with Buffer is not defined Cloudflare Node compatibility is absent. Confirm compatibility_flags = ["nodejs_compat"].
Page is unstyled or /_astro/* is 404 A stale base path or wrong deployment target is being used. Confirm base is not set and deploy Worker + Assets using the generated config.

11. Recovery playbooks

A. A revision PR is open but should be superseded

  1. Save a new revision from the dashboard — the CMS closes the older PR with a linking comment.
  2. Review the newer PR; ignore the superseded one. It is never reopened.

B. Merged but not Published

  1. Open GitHub Actions and find the run for the merge commit.
  2. If the deploy succeeded but the callback failed, fix the callback configuration and use a controlled operator procedure to send a newly timestamped, freshly HMAC-signed callback carrying the deployed SHA and terminal status. An expired callback cannot be replayed verbatim.
  3. If the deploy failed, fix the cause and re-run the workflow on the same commit. Do not create a second PR merely to redeploy.

C. A mistake was merged

  1. Trigger a revert PR from the dashboard (section 7).
  2. Review and merge it like any other PR; the site rolls back through the normal deploy path.

D. A secret was exposed

  1. Revoke the exposed GitHub or Cloudflare credential immediately.
  2. Generate a replacement and update every location that shares it.
  3. Redeploy the Worker if a Worker secret changed.
  4. Run a login and a revision-PR smoke test.
  5. Record the rotation date without recording the secret value.
Do not “fix” production state by hand first

Do not hand-edit KV, force-push a merged branch, or reopen a closed PR. The states exist to keep every production change reviewed and every revision traceable. Investigate first, then act through the dashboard or GitHub.

12. Release checklist

  • The post has the intended title, slug, date, featured image, required alt text, and status.
  • Every image reference resolves in the revision; the media contract limits are met.
  • The revision PR contains the correct Markdown + media and the PR metadata block.
  • No older PR for the same post is left open when it should be superseded.
  • The owner has reviewed the PR diff on GitHub.
  • The merge is to main; merged PRs are never force-updated.
  • GitHub Actions repository secrets are present and not expired.
  • The deploy run is green and the signed callback records the deployed SHA.
  • The dashboard shows Published for the merged revision.
  • The public blog route shows the intended content and drafts remain absent.
