# ADR 0011 — Repository media contract for Markdown posts

- **Status:** Accepted
- **Date:** 2026-08-06
- **Context:** CMS-edited Markdown posts commit their images into the same repository and the same pull request as the post (ADR 0009). The pre-contract state was inconsistent and collision-prone: images lived in a shared `src/images/{bsm,ref}/` pool referenced **by basename** (`images.ts` split on `/` and looked up the tail), one post referenced a path containing a space, the blog page used the post title as the image's alt text, and there was no upload validation beyond the build-time "missing asset" throw. This ADR fixes the contract for where images live, how they are named, referenced, validated, replaced, and rolled back.

## Decision

- **Atomicity:** Markdown and its images land in one revision/PR; the per-post media folder makes the revision the atomic unit.
- **Location:** per-post folders `src/images/blog/<post-slug>/` under the existing `src/images/` tree. Posts stay flat; catalog and blog share one resolver. The shared `src/images/ref/` pool becomes legacy and migrates as part of the cleanup task.
- **References:** frontmatter `image` stores an **explicit path relative to `src/images/`** (`blog/<slug>/cover.jpg`). The resolver resolves explicit paths; basename fallback is kept only for legacy catalog references during migration.
- **Types and limits:** JPEG, PNG, WebP only. SVG is excluded (XSS surface in rendered Markdown); GIF/AVIF are excluded because Astro already emits optimized AVIF/WebP at build. Max 5 MB per file, 8000 px longest edge, validated by magic bytes (not extension) server-side at upload. Originals are committed as uploaded; Astro optimizes at build (`_astro/*` hashed output is the canonical URL source per ADR 0010).
- **Naming:** sanitized `[a-z0-9-]` only, generated by the CMS (never the user's raw filename). Featured image: `cover.<ext>`; body images `01-<name>.<ext>`, `02-<name>.<ext>`, …; duplicate names get a `-2` suffix.
- **Alt text:** a required `imageAlt` field accompanies `image` in the schema (replacing the previous `alt={title}` behavior); body-image alt text lives in the Markdown (`![alt](path)`) and is authored in the editor.
- **Replacement and deletion:** uploading an existing filename in a new revision overwrites the bytes in that revision's branch (git history records the change; exact-content provenance still holds because the file is captured per revision). Deletion is allowed only when the same revision's Markdown/frontmatter no longer references the image. Unreferenced orphans after merge are kept; cleanup is out of scope.
- **Missing references:** the CMS resolves every `image:` and `![...]` reference against the revision branch **before opening the PR** (a broken PR cannot be created); the Astro build remains the backstop and fails on any missing asset, so CI never deploys a broken site.

## Rejected alternatives

- **Per-post content folders (`src/content/blog/<slug>/index.md` + images beside the post) with Astro's native `image()` schema helper:** cleaner in theory, but a content-tree restructuring the migration would have to absorb, for no gain over the incumbent resolver.
- **Kept basename-only resolution:** collision-prone (two files, same basename, silent last-wins); the source of the space-in-path breakage.
- **Server-side conversion/normalization of uploads:** the CMS commits originals and lets Astro optimize; conversion adds a failure surface for no fidelity gain.

## Consequences

The resolver, the blog schema (new `imageAlt`, required), the upload path in whichever editor survives (decision owned by the editor-boundary ticket), and the PR-creation gate (dangling-reference validation) all follow this contract. The migration task owns moving legacy `src/images/ref/` files into per-post folders and rewriting legacy basename references to explicit paths.
